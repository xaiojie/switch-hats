> 目的：让下一个接手的人不必再翻日志和聊天记录，直接知道**哪些已排除、哪些还活着、下一步做什么**。

## 0. 一句话

mod 加载**确实通了**（R6/R7 的 Lua 错误弹窗证明 `modmain` 执行、回调注册、世界生成期被调用），
但游戏随后在**渲染线程**以同一条原生空指针崩溃（`0x4A8 / PC +0x8ae4`）退出。
十一轮改动都没有撼动这个签名，根因仍未定位。

## 1. 目标与验收

- 目标：Atmosphere LayeredFS 注入，让 Switch 版 DST（`010090100E334000`，游戏版本 `Rev: -1500 SWITCH`）
  加载一个零资产的最小 Lua mod。
- 验收（三级）：① 主菜单不崩 → ② 「创建游戏」文字后出现 `[DST-MOD Rx]` 标记（证明 modmain 执行）
  → ③ 新世界出生背包多一块金块（证明 AddPlayerPostInit 回调生效）。
- **当前进度：① ✅（R5 起稳定）、② ✅（R6 截图证据）、③ ❌ 未达成**（世界生成期原生崩溃）。

## 2. 常量事实（每轮都相同，可直接当判据）

```
Result: 0x4A8 (2168-0002)      Type: Data Abort      Address: 0x0
Crashed thread: RenderThread
PC: dontstarve_nx.nss + 0x8ae4   LR: +0x8ac8   X[00] = 0
ReturnAddress: +0x10cac / +0x9008 / +0x2c35ec
Build ID: 4D0E7A46016CAF6FA1A34144EF402E82AFE6E018000000000000000000000000
```

- 崩溃时线程全景：Server×2、UpdateJobThread_0..4、AsynTextureLoadthread×2、Ping、FMOD×3、
  NEX、NXInputManager、SystemService 全在跑 → **不是启动早期崩溃**。
- 屏幕上**没有 Lua 文本**，只有系统弹窗「由于发生错误，软件已关闭」= 进程级崩溃。
  Lua 报错会走游戏自己的「警告！下列模组导致了故障」弹窗（见 R6），两者要分清。

## 4. 崩溃点逆向（对 `main` NSO，文件偏移 = 模块偏移 + 0x100）

`+0x8ae4` 所在函数起点约 `+0x8934`，前面的循环遍历一个数组、校验 `[x20+0x70] == 4`、`bl #0x51b24`：

```asm
+0x8ad4: ldr x8, [x20, #0x158]   ; 取子对象
+0x8ad8: cbz x8, #0x8a30         ; 为 NULL 就跳过 → 此刻非 NULL
+0x8adc: ldr x0, [x8, #0x90]     ; x0 = 子对象+0x90 的字段 → 读到 0
+0x8ae0: mov v0.16b, v8.16b      ; SIMD 拷贝（颜色/纹理/batch 数据）
+0x8ae4: ldr x8, [x0]            ; ← CRASH，对 NULL 取虚表
+0x8ae8: ldr x8, [x8, #0x10]
+0x8aec: blr x8                  ; 虚函数派发
```

含义：**渲染对象 `x20` 的子对象存在，但它的 `+0x90` 字段（大概率是 texture/material 句柄或 draw-list 指针）是 NULL**，
随后对 NULL 做虚调用。SIMD 指令 + RenderThread + 有 `AsynTextureLoadthread` 在跑 → 这是**渲染批次里的资源对象**。

三层调用链：`+0x2c35ec`（`blr x8`，x8=[x8,#0x10]）→ `+0x9008`（`blr x8`，x8=[x8,#0x30]）→
`+0x10cac`（`bl #0x8934` 进入崩溃函数）→ 崩。

## 6. 还站得住的假设 + 具体实验（按性价比排序）

**N1（最推荐）把探针从 `print` 改成写文件。**
`print` 在主机上没有可读出口。在 modmain 与 overrides 里用 `io.open("/sdmc:/dst-probe.log","a")`
（备选 `sdmc:/switch/dst-probe.log`）记录：`package.assetpath` 条目数与内容、`LoadMods` 进出、
`IsInFrontEnd()`、`TheNet:IsDedicated()`、modmain 执行、`AddPlayerPostInit` 回调触发、世界生成开始/结束。
**目的**：第一次拿到"崩之前最后执行到哪"的白盒证据，而不是靠猜。若 io 被沙箱禁掉，退而用
`TheSim:SendCommandToInstance` 打到另一个实例再触发同样的写文件（R8 的 probe 已有发送框架可复用）。

**N2 分离「assetpath 插入」与「modmain 执行」。**
新诊断模式：让 `LoadMods` 插入 assetpath 条目 → 立刻删除 → **不执行 InitializeModMain**（跳过 modmain）。
- 若仍崩 → 根因在 native 侧对 mod 目录的注册/扫描（Lua 删不掉的那部分）。
- 若进菜单正常 → 根因在 modmain 执行产生的 Lua 状态（回调/环境），而不是目录本身。

**N3 分离「目录存在」与「LoadMods」。**
保留 `mods/dst-test-mod/` 文件但让 `LoadMods` 完全不跑（R2 的 exact replay，但用 R9 的 frontend 门版本）。
R2 当时是全局开关时代，变量没控制干净，值得用干净版本重跑一次。

**N4 换 mod 目录位置，绕开 LayeredFS 新增目录。**
把测试 mod 放到 `sdmc:/mods/dst-test-mod/`，`MODS_ROOT = "/sdmc:/mods/"`。
排除「romfs 只读层运行期新增目录」这一条（主机版资源系统可能只对挂载时已存在的目录建索引）。

**N5 版本对齐。**
卡上游戏 `Rev: -1500 SWITCH`；解包用的 NSP 更旧（**证据**：`multiplayermainscreen.lua` 报错行号
安装版 908 / 解包版 988）。找与安装版一致的 NSP 重新解包，让 overrides 的注入上下文与安装版严格一致。

**N6 把 mod 拆到最小。**
`client_only_mod = true` + modmain 里只留 `print`/写文件，**不注册任何 PostInit**。
- 若仍崩 → 与回调无关，纯属"加载了 mod"。
- 若不崩 → 逐步加回 `AddPlayerPostInit`，二分到具体回调。

**N7 只在 server 实例加载，不碰 frontend。**
R9 是"只在 frontend 加载"。反过来做：frontend 完全不碰，只让 server 侧加载（`LoadMods` 在
`IsInFrontEnd()` 为真时直接原样调用原函数）。借此判断崩溃属于哪个实例的渲染管线。

## 9. 雷区（踩过的都记在这）

- **不要整文件替换** `mods.lua` / `modindex.lua` / `multiplayermainscreen.lua`：安装版比解包 NSP 新，
  旧盖新会 `0x2F6202 User Break`（栈 `open64 → fopen → nss+0x43f80`）。
- 主机版缺 PC 专有 API：已知 `tooltipGetButtonStyle`、`TheSim:QueryTopMods`；遇到
  `attempt to call ... (a nil value)` 先补空实现。
- 主机版 Lua 没有 5.0 的隐含 `arg` 表，`runmodfn` 里 `unpack(arg)` 必炸（R6 的弹窗就是它）。
- mod 环境只给 `GLOBAL`，不给裸 `SpawnPrefab`；且要判 `TheWorld.ismastersim`。
- `TheSim:GetModDirectoryNames()` 在主机上返回空 → 必须靠 `forceddirs` 注入目录名。
- 每次改完必须**完全退出游戏**再进（热重载不生效），并且推送前清掉卡上残留文件。
- 崩溃报告文件名里的数字是序列号，不是时间；排序用序列号 + 截图时间戳。
- 判断"是否真的崩了"：有系统级「由于发生错误，软件已关闭」= 原生崩；
  有「警告！下列模组导致了故障」= Lua 层错误（游戏还活着）。
